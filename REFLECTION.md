## Question 1 

For this question, I chose StageMoveForm, which is in my hiring/forms.py and inherits from forms.Form. This class checks if a stage move is allowed before anything is changed. So in this case, if hiring staff click a move button on the pipeline page, HTMX will send a POST to the application_move() view that's in views/pipeline.py. From here, the view runs the form, and if it's valid, it calls move_to() which will change the stage and saves the history. If comes out not valid, the error shows up as a toast. Now for the forms.ModelForm, this class is in JobOpeningForm, which is also in my hiring/forms.py. This class is built from the JobOpening model and is used in job_create() and job_edit() in views/jobs.py. When valid, form.save() will save the job and its skills, which then redirects to the job page. If it's not valid, nothing will be saved to the database and the user won't be redirected to another page and the form will reload with an error. The main difference between these is that a  ModelForm is connectred to a model and saves to the data. But a regular form will just check the input and my project code decides what happens next. I picked a plain Form for stage moves during my grill session so that every move has to go through move_to() and can't skip the rules or the history.

## Question 2

JobOpening and Skill are connected with skills = models.ManyToManyField(Skill) on JobOpening. This means that a job can need a lot of skills, but one skill can be on a lot of jobs. For this example, a single foreign key would only let each job have one skill, or each skill belong to only one job. What could go wrong with this is that multiple jobs could require a skill, but this would make a skill only available for a single job and not be able to be used again. Such as if 3 jobs need python, only one job could claim it. Django made the association table automatically, which it's called hiring_jobopening_skills, and it just stores pairs of job IDs and skill IDs. It's in the 0003_jobopening.py migration.

## Question 3 

For this question, I chose my application-state prototype. This prototype was used to figure out which stage moves the system should allow. During this session, I asked for options c and d to be compared side by side. Option c would allow the system to move forward, go back one stage, and reopen rejected or withdrawn applicants. In contrast, option d would allow going back to any stage, but moving to ired, rejected, or withdrawn would be final. I decided to choose option c because with option d, once an applicant was rejected, there was no way to undo it. The applicant would be stuck in a rejected stage with no way to go back to the previous stages. But with option c, there was an option to reopen an applicant that would take them back to the stage they were previously on before rejection. When I was looking at the prototype, I also found that option C would allow an applicant to skip from the Interview stage directly to Hired. To fix this, I made Hired only reachable if the applicant is in the Offer stage. I also made moving to the same stage just do nothing rather than show an error message. This is in my Stage Rules section in the PRD, in allowed_moves() in stages.py and also in move_to() in models.py.
